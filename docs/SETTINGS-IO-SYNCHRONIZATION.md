# Windows の設定 I/O 同期規約 v1

同じ Windows ホストで同じユーザーとして動く協調プロセスは、設定の読取りと保存に一つの名前付き mutex を使う。通常版、Portable 版、別の実行ファイル、異なる保存先も同じロックを使う。設定先の解決、Portable marker、設定ファイルの形式と対応媒体は従来の規則に従う。

## 同期名とアクセス権

1. 現在の製品プロセスのアクセストークンから、妥当性と長さを確認した TokenUser のバイナリ SID を取得する。
2. 固定 ASCII 文字列 `clipss2.settings.io.user.v1`、NUL 1 バイト、SID バイナリを順に連結し、SHA-256 を計算する。SID は Windows API が示す長さ分のバイトを使う。
3. ハッシュを小文字 16 進数 64 桁にし、`Global\clipss2.settings.io.user.v1.` の直後へ置く。ユーザー名、セッション ID、アプリの版、EXE と保存先のパスは名前の生成に使わない。

名前が同じユーザーのセッション間で一致しても、取得には Windows のアクセス制御と整合性レベルが適用される。オブジェクトの所有者を当該ユーザーとし、明示的 DACL の許可 ACE はその SID の `SYNCHRONIZE | READ_CONTROL` 一件とする。ハンドルは継承不可。新規・既存とも待機前に所有者、DACL、ハンドル属性を検査する。作成・検査・待機の失敗は設定 I/O の失敗として返す。診断には段階とエラー番号を記録する。SID、ハッシュ、同期名は記録しない。

## 取得順序と設定の公開

名前付き mutex、プロセス内 mutex の順に取得し、逆順に解放する。単調増加する時計に基づく取得予算は合計 250 ms。名前・権限・パスの解決、ファイル I/O、OS スケジューリングはこの予算の対象外。タイムアウト時は設定の読取りや保存を抑止する。初回読取りが失敗した個体は、安全な既定値をそのまま永続化せず、改めて設定を読み取ってから復旧する。

初回読取りは設定先を決めるための存在確認から、保存は事前読取り・schema 判定・必要なディレクトリ作成から、一時ファイルの書込み、flush、close、置換、失敗時の片付けまで同じ排他に含める。通常読取りと保存内部の読取りは同じ処理を使い、保存内部でロックを再取得しない。UI 通知、外部コールバック、キャプチャワーカーの実行前に解放する。

`WAIT_ABANDONED` で所有権を得た場合も、正式ファイルを読み直して schema・サイズ・読取り状態を検証する。過去の一時ファイルは残し、この保存で作ったものだけを管理する。公開後のロック解放失敗は診断に残し、公開済みの保存は成功として扱う。

## 保存契約と対応範囲

先に公開された将来 schema は、協調する旧 schema writer の事前読取りで検出し、保存を拒否する。旧 schema writer が先に排他区間に入れば、協調する将来 writer はその区間が終わるまで待つ。同じ schema 内では最後に成功した全項目の保存を採用する。古いスナップショットの保存で別の変更が戻る可能性がある。

旧版や外部ツールの非協調な書込み、別ユーザーや別ホストからの書込み、共有違反、OS 障害・停電はこの同期規約の保証範囲外。ファイルシステムや保存先の種類はロックの条件にしない。同じユーザーの別の保存先への操作も待つため、低速な保存先の処理は別の保存を待機させることがある。将来版でも、互換性を確保するため名前の生成、namespace、アクセス権、排他範囲を共有する。
